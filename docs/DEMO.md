# Portfolio demo guide

This five-minute walkthrough highlights the engineering decisions behind TraceAid rather than only showing a chat-like AI result.

## Before the demo

For a no-install browser tour, open [the interactive demo](https://manostsagkos.github.io/traceaid-ai/). It presents six prepared reports generated by the real Python rules engine. Custom input and AI run in the local application:

```bash
python -m pip install -e ".[dev]"
uvicorn traceaid.main:app --reload
```

Keep live probes disabled and use a synthetic built-in example. The full deterministic workflow requires no secret and works offline.

For a terminal-first preview, run:

```bash
traceaid demo expired-token --format markdown
```

## Suggested walkthrough

### 1. Start with a failed request

Open `http://localhost:8000`, select the synthetic `401 Unauthorized` example, and point out that `curl` parsing is also available through the API endpoint.

Emphasize that parsing does not execute the command and that the Authorization value is synthetic.

### 2. Diagnose without AI

Leave AI and live probing off. Run the diagnosis and show:

- authentication category, severity, and confidence;
- exact evidence used by the deterministic engine;
- ordered fix steps;
- redaction in the returned report and exported artifacts.

This demonstrates that the product remains useful without an external model and that its baseline result is explainable.

### 3. Show developer-ready artifacts

Open the generated `curl`, Python, and `pytest` tabs. Explain that method/media-type corrections are supported by the observed evidence, while secrets and endpoint-specific validation fields need a developer's review. Generated tests assert success against a real endpoint only after the fix is supplied; the project tests these templates with mocked HTTP.

Export both Markdown and JSON. The Markdown output is for an issue or incident note; JSON is suitable for CI or another developer tool.

### 4. Explain the AI boundary

If a disposable development key is configured, enable AI and repeat the synthetic example. Show the mode/source indicator and explain that:

- only minimized, redacted evidence reaches the provider;
- the Responses API output is schema validated;
- malformed output, timeout, or provider failure falls back to the rule result.

Do not reveal `.env`, terminal history containing a key, or provider dashboards during a recording.

### 5. Close on security and delivery

Briefly show `/docs`, the passing test suite, and the architecture diagram. Mention that live probes are double opt-in, protected by SSRF checks, bounded by timeout/size, and still expected to run behind network egress controls in production.

## CV talking points

- Why a deterministic-first architecture is more reliable than unconditional LLM calls.
- How structured outputs turn an LLM response into a validated application contract.
- How SSRF risk changes when a diagnostic app can replay arbitrary URLs.
- Why redaction must happen before logging, exporting, and provider calls.
- How mocked boundary tests make API integration and provider failure reproducible in CI.
